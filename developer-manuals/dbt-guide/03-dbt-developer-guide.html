MANUAL 03 / 01

dbt：基本構成からベストプラクティスまで

架空の販売データで学ぶ、構成・比較・変更・品質・費用。

dbtは、DWHに入っているデータを、分析しやすいTableやViewへ変換するための開発・実行の仕組みです。SQLのSELECT、YAMLの設定、Jinjaの参照を組み合わせ、依存関係・テスト・文書を管理します。

役割この資料での位置づけ
データの取り込みCloud Run functions、ETL/ELTコネクター等が元データをBigQueryへ送る
インフラ構成Terraformがデータセット、IAM、実行基盤等を管理する
データ変換dbtがSQLモデルをBigQuery上で実行する
データ利用Looker Studio等が整えたMartを参照する

同梱内容は、最小プロジェクト、パターン比較プロジェクト、12ケースのメリット・デメリット、初回/変更後CSV、オフライン検算です。実在企業の導入事例や本番データではありません。

出典：[01] dbtの全体像・実行系, [06] SQLモデル

01 実行系と構成を区別する

04 最初の実行手順

まず最小プロジェクトで、seed→Table→テストの関係を確認します。

.\scripts\setup.ps1
$env:DBT_PROJECT = "YOUR_PROJECT_ID"
$env:DBT_LOCATION = "asia-northeast1"
gcloud auth application-default login
.\.venv\Scripts\dbt.exe debug --project-dir projects/minimal --profiles-dir profiles
.\.venv\Scripts\dbt.exe seed --project-dir projects/minimal --profiles-dir profiles --full-refresh
.\.venv\Scripts\dbt.exe build --project-dir projects/minimal --profiles-dir profiles --exclude resource_type:seed

BigQueryコンソールで開発用データセットを準備し、読み取り・書き込み・ジョブ実行の権限を確認します。デフォルトの出力先は最小版がdbt_demo_minimal、比較版がdbt_demo_patternsです。

本番での取り込みは別の仕組みを使います。この教材はseedで架空の元テーブルを作るため、先にseedを実行します。Sourceの定義だけでは、seedとSourceの作成順序は自動で結びつきません。

最小モデルのSQL
-- 粒度：注文日ごとに1行。教材ではpaidのみを売上に含めます。
select
    order_date,
    count(*) as paid_order_count,
    sum(round(amount * (1 - discount_rate), 2)) as net_revenue
from {{ ref('raw_orders') }}
where lower(trim(status)) = 'paid'
group by order_date

初回の期待値は売上680、paid注文4件、3日分です。詳しい手順はdocs/01-quickstart.mdにあります。

05 Materializationの選び方

同じSELECTでも、保存方式で鮮度・費用・速度・保守性が変わります。

方式強み弱み・適する条件
view元の現在値を参照しやすい。結果Tableを保存しない照会のたびに計算。少量・軽量・低頻度に向く
table完成した結果を高速に参照できる候補再buildまで古い。全件再計算の費用
incremental処理対象の限定、更新・追記・範囲再作成遅延・削除・再実行・復旧の設計が必要
ephemeral物理中間物を作らずCTEへ組み込む各下流で計算。長いSQL・デバッグ負担
materialized_viewDWHが対応する結果保持・更新を利用アダプター・エンジン・SQL制約を確認

小さいTableを毎日再作成する処理へ、必ずIncrementalを入れる必要はありません。全件再作成の単純さと、差分処理を維持する開発・運用コストを比べます。

出典：[07] Materialization, [10] BigQuery設定, [11] Incremental, [29] BigQuery論理View, [30] BigQuery Materialized View

06 P01–P03：View・全件Table・共通Table

同じ販売データを、参照頻度と再利用範囲で比較します。

P01

View中心の構成

小さい参照表や、常に最新状態を見たい低頻度レポート。

比較内容
メリット結果Tableの定期再作成が不要。SQLの定義を共有しやすい。
デメリット参照のたびに元データの計算が必要。高頻度BI・重い結合では費用と遅延が増えやすい。
確認例phase2のseed後、Viewは再buildしなくても基礎データの変更を参照できます。SQL定義を変えた場合は再buildが必要です。
注意点Viewは計算結果のキャッシュではありません。Viewを増やすだけで費用が本数倍になるとも言えず、実際のSQLと処理バイトを確認します。

サンプル：projects/patterns/models/patterns/p01_sales_view.sql

サンプルを開く
{{ config(materialized='view') }}
select order_date, count(*) as paid_order_count, sum(net_amount) as net_revenue
from {{ ref('int_paid_orders_ephemeral') }}
group by order_date
P02

小規模な全件Table再作成

日次の販売レポート。数千～数万行程度の小さい教材から始める場合。

比較内容
メリット変更・物理削除を現在の入力から取り込みやすい。単純なSELECTで保守できる。
デメリット更新のたびに対象全体を再計算する。大量・高頻度では負担が増える。
確認例phase1は売上680、phase2は349。最終Tableはdbtで再作成するまで変わりません。
注意点少量ならIncrementalを導入する運用・調査コストの方が大きい場合があります。

サンプル：projects/minimal/models/mart_sales_daily.sql

サンプルを開く
-- 粒度：注文日ごとに1行。教材ではpaidのみを売上に含めます。
select
    order_date,
    count(*) as paid_order_count,
    sum(round(amount * (1 - discount_rate), 2)) as net_revenue
from {{ ref('raw_orders') }}
where lower(trim(status)) = 'paid'
group by order_date
P03

共通の重い結合を中間Tableに保存

同じ注文・顧客結合を複数Martや複数BIから利用する。

比較内容
メリット結合結果を再利用でき、下流のSQLを小さくできる。
デメリット保存と更新の費用が追加。中間Tableが古いと下流も古くなる。
確認例p03_sales_by_segmentとp09_wide_bi_tableが同じ中間結果を参照します。顧客102の変更後に再buildするとpremiumに集計されます。
注意点1対多Joinで注文が増殖すると集計が水増しされます。キーの一意性を先にテストします。

サンプル：projects/patterns/models/patterns/p03_orders_enriched_table.sql

サンプルを開く
{{ config(materialized='table', partition_by={'field':'order_date','data_type':'date'}, cluster_by=['customer_id']) }}
-- 複数Martで使う共通の結合結果を保存する例です。
select o.order_id, o.customer_id, o.order_date, o.status, o.net_amount,
       c.segment, labels.status_label
from {{ ref('stg_orders') }} as o
left join {{ ref('stg_customers') }} as c using (customer_id)
left join {{ ref('status_labels') }} as labels using (status)

MANUAL 03 / 08

07 P04–P06：Incrementalの3つの使い方

追記、キー更新、パーティション再構成は異なる設計です。

P04

不変イベントの追記型Incremental

event_idが一意で、既存イベントの更新・削除がないログ。

比較内容
メリット新しいIDだけを追加する。再実行の重複を避けやすい。
デメリット本例のNOT EXISTSは既存対象の読取が増える。既存イベント修正は拾わない。
確認例phase1の3イベント→phase2の4イベント。同じ入力を再実行すると新規対象SELECTは0件です。
注意点BigQuery用サンプルはmerge戦略です。他アダプターのappend設定をそのまま持ち込まないでください。入力のuniqueテストも必要です。

サンプル：projects/patterns/models/patterns/p04_events_incremental.sql

サンプルを開く
{{ config(materialized='incremental', incremental_strategy='merge', unique_key='event_id', on_schema_change='fail') }}
-- イベントは不変という前提。BigQueryのmergeで新規IDを追記します。
-- 全対象とのNOT EXISTS比較は読み取り費用が増えるため、大規模化時は別途最適化します。
select e.event_id, e.order_id, e.event_type, e.event_at
from {{ ref('stg_events') }} as e
{% if is_incremental() %}
where not exists (select 1 from {{ this }} as old where old.event_id = e.event_id)
{% endif %}
P05

更新時刻＋MERGEによる差分反映

注文金額・状態が更新され、信頼できるupdated_atと主キーがある。

比較内容
メリット過去キーの修正と再実行に対応できる。更新対象を限定できる。
デメリット物理削除は残る。lookbackより古い到着は拾えない。宛先MERGEの読取も必要。
確認例phase2の金額・状態変更は反映しますが、注文6の120が残り、paid合計469になります。現在の正しい349との差分を確認します。
注意点unique_keyはDB制約の自動保証ではありません。宛先を直近日だけに絞るincremental_predicatesで過去キーが不一致になると、重複を作ることがあります。

サンプル：projects/patterns/models/patterns/p05_orders_merge.sql

サンプルを開く
{{ config(materialized='incremental', incremental_strategy='merge', unique_key='order_id',
          on_schema_change='fail', partition_by={'field':'order_date','data_type':'date'}, cluster_by=['order_id']) }}
-- 再実行時は更新時刻に基づくlookback。物理削除は、このmergeだけでは伝播しません。
select order_id, customer_id, order_date, status, net_amount, updated_at
from {{ ref('stg_orders') }}
{% if is_incremental() %}
where updated_at >= timestamp_sub(
    coalesce((select max(updated_at) from {{ this }}), timestamp('1900-01-01')),
    interval {{ var('merge_lookback_days', 3) }} day
)
{% endif %}
P06

日付単位のinsert_overwrite

直近数日の注文・集計が修正され、対象日を全件再構成できる。

比較内容
メリット対象日に含まれる削除も反映できる。処理範囲を日付で管理しやすい。
デメリット対象日ごとに全行が必要。選び忘れた過去日は更新されない。
確認例rebuild_datesの3日を再構成し、phase2のpaid合計は349になります。空のパーティションを消すには置換対象日を明示します。
注意点変更行だけをSELECTしてpartitionを置き換えると、変更のない正しい行が消えます。

サンプル：projects/patterns/models/patterns/p06_orders_insert_overwrite.sql

サンプルを開く
{% set partitions_to_replace = [] %}
{% for date_value in var('rebuild_dates') %}
  {% do partitions_to_replace.append("date('" ~ date_value ~ "')") %}
{% endfor %}
{{ config(materialized='incremental', incremental_strategy='insert_overwrite',
          partition_by={'field':'order_date','data_type':'date'}, partitions=partitions_to_replace,
          on_schema_change='fail') }}
-- 対象日に属する現在の全行を取得します。変更行だけを返すSQLにしてはいけません。
select order_id, customer_id, order_date, status, net_amount, updated_at
from {{ ref('stg_orders') }}
{% if is_incremental() %}
where order_date in ({{ partitions_to_replace | join(', ') }})
{% endif %}

is_incremental()の分岐は、初回・--full-refresh時の全件処理にも成立させます。unique_key、重複、NULL、lookback、updated_atの意味を確認します。on_schema_changeだけで過去行の新列値や計算変更を埋め直せるとは限りません。

08 P07：Snapshotで以前の状態を残す

「最新のTable」と「以前の状態を残す履歴」を分けます。

P07

Snapshotによる顧客履歴（SCD Type 2）

顧客セグメントが変更されても、以前の状態を残して分析したい。

比較内容
メリットdbt_valid_from/toで有効期間を保存できる。更新されたマスターの履歴を追える。
デメリット継続実行と保存費用が必要。実行の間に起きた全変更は保証できない。
確認例phase1の後にphase2を観測し、顧客102の旧segmentを閉じ、新segmentを追加。104の削除はhard_deletes=invalidateで旧行を閉じます。
注意点timestamp戦略はupdated_atが正しく進むことが前提。SnapshotはBigQueryのTable snapshotやバックアップとは別です。

サンプル：projects/patterns/snapshots/customers.yml

サンプルを開く
version: 2
snapshots:
  - name: snap_customers
    relation: source('demo_raw', 'raw_customers')
    config:
      unique_key: customer_id
      strategy: timestamp
      updated_at: updated_at
      hard_deletes: invalidate
    description: "観測時点の顧客セグメント履歴。削除を検知したら以前の行を無効化します。"
過去時点の顧客属性を参照するSQL例
-- Snapshotが存在する場合の履歴参照例。既定のdbt実行対象外です。
-- 教材は注文日のUTC 00:00を比較時刻にします。実務では注文の正確な時刻・業務TZを定義します。
select o.order_id, o.order_date, h.segment as segment_at_order_date
from {{ ref('stg_orders') }} as o
left join {{ ref('snap_customers') }} as h
  on o.customer_id = h.customer_id
 and timestamp(o.order_date) >= h.dbt_valid_from
 and (h.dbt_valid_to is null or timestamp(o.order_date) < h.dbt_valid_to);

この例は注文日UTC 00:00で比較する教材です。実務では注文時刻、業務タイムゾーン、有効期間の境界を定義します。履歴を開始する前の過去データや、観測の間に起きた全変更を自動で復元するものではありません。

出典：[12] Snapshot, [13] Snapshot削除

09 P08–P09：小さい共通処理とBI向けTable

再利用したい「式」と、再利用したい「計算結果」を区別します。

P08

Seed・Macro・Ephemeralの小さな共通処理

少数の状態コード、日本語ラベル、割引計算、軽い1回利用のフィルター。

比較内容
メリット小さい参照表をGitでレビューでき、式をMacroで共有できる。Ephemeralは中間物理Tableを作らない。
デメリットseed変更にはロードが必要。Macroを多用するとSQLが追いにくい。Ephemeralは単独参照・調査しにくい。
確認例status_labels.csvとnet_amount.sql、int_paid_orders_ephemeral.sqlも読みます。注文件数が結合で増えないことを確認します。
注意点seedは大量データの取り込みや機密情報の保存先ではありません。EphemeralのSQLは各下流へ組み込まれ、計算再利用を保証しません。

サンプル：projects/patterns/models/patterns/p08_seed_lookup.sql

サンプルを開く
{{ config(materialized='view') }}
select o.order_id, o.status, labels.status_label
from {{ ref('stg_orders') }} as o
left join {{ ref('status_labels') }} as labels using (status)
P09

BI向けの横持ちTable

Looker Studioから複数のdimensionを一緒に使い、参照時のJoinを減らしたい。

比較内容
メリット利用者がSQLのJoinを書かずに使える。参照クエリの負荷を前処理へ移せる。
デメリットdimensionの重複保存と更新コスト。履歴・多対多・粒度を誤ると二重集計になる。
確認例注文ID粒度で入金済み注文を公開します。日次粒度のmart_sales_dailyとは違うので件数の意味も確認します。
注意点500列を無条件に用意せず、BIの利用列を絞ります。Fact＋Dimensionの構成との比較は読取頻度と保守性で判断します。

サンプル：projects/patterns/models/patterns/p09_wide_bi_table.sql

サンプルを開く
{{ config(materialized='table', partition_by={'field':'order_date','data_type':'date'}, cluster_by=['customer_id']) }}
-- Looker Studio向けに必要な列だけ用意する、注文粒度の横持ちTableです。
select order_id, order_date, customer_id, segment, status_label, net_amount
from {{ ref('p03_orders_enriched_table') }}
where status = 'paid'
割引後金額を生成するMacro
{% macro net_amount(amount_column, discount_column) -%}
round(cast({{ amount_column }} as numeric) * (1 - cast({{ discount_column }} as numeric)), 2)
{%- endmacro %}

MacroはSQLを生成する仕組みで、結果のキャッシュではありません。Ephemeralも共通の計算結果を1回だけ保存する仕組みではありません。重い結果を複数で使う場合はTable化などを別に比較します。

BI向け横持ちTableは便利ですが、注文・顧客・日付などの粒度を混ぜないことが重要です。Fact＋Dimensionの構成では属性再利用がしやすく、横持ちでは利用者のJoinが少なくなる、という比較から選びます。

10 P10：Data test・Unit test・Contract・Freshness

それぞれが確かめる内容は異なります。

P10

テストと契約による公開品質の担保

売上指標を複数部署へ配布し、変更時に壊れた列や計算を検出したい。

比較内容
メリットキー・型・業務整合・境界のチェックをコード化できる。
デメリットテストもクエリ費用・実行時間を使う。合格は業務の全意味を保証しない。
確認例Data tests、Unit test、Contract、tests/assert_sales_total_matches_base.sqlを実行対象として確認します。

13 ベストプラクティスの判断基準

最初に品質の意味を定義し、テスト・運用・費用へ結びつけます。

観点基準と終了条件
粒度「注文IDごと」「日付ごと」等を1行の意味として定義。キーの重複テストを置く
金額通貨、税、割引、返金、丸め、売上計上時点を業務側と定義。NUMERIC等を検討
Source取り込み済みテーブルを定義。元データの取り込み処理と混同しない
Staging改名、型、基本計算、状態正規化。集計・多表結合は必要性で別工程へ
無意味な層完全ミラーViewを必須にしない。モデル分割に役割があるか確認
ref/source依存を明示し、環境名をSQLへ直接固定しない

Incremental更新・遅延・削除・空パーティション・再実行・full-refreshを設計
Data testsunique/not_null/relationships/accepted_valuesに加え業務整合を確認
Unit tests境界、丸め、状態変換を少量fixtureで検証
Freshness最終更新時刻とロード時刻を区別。取り込み停止の監視は別コマンド・閾値で定義
Contract重要な公開モデルの列名・型を固定。正しい金額や非NULLまで保証するものではない
公開全DAGの更新が1トランザクションとは限らない。テスト後の公開切替を必要に応じて設計
個人情報Gitのseedへ実データを入れない。アクセス権・マスキング・ログ・成果物も確認
環境個人・CI・本番のdatasetと権限を分離。custom schemaの既定挙動も確認
実行同じIncremental/Snapshotを同時に更新しない。取り込み完了後に実行する
ドキュメント定義、責任者、更新頻度、利用先（Exposure等）を残す
費用build・テスト・Snapshot・BI照会・保存・外部実行基盤を合算して比較

14 BigQueryのコストと性能を改善する

dbtの実行費用だけでなく、テスト・BI参照・保存を含めて比較します。

改善候補効果と注意点
列・行を絞るSELECT *の持ち回りを減らす。不要列や対象外期間を読まない
パーティション・クラスタ実際のWHEREとキーに合わせる。設定しただけで必ず安くなるわけではない
重い共通結果のTable化build時の費用・保存費用を増やし、下流の反復計算を減らす候補
Incremental入力側と宛先側の読取を測る。削除・遅延・過去更新の正しさを守る
テスト範囲重要キーと業務整合を優先。コストを理由に必要な検査を失わない
threads同時実行数。増やしても読取バイトが減るわけではなく、クォータ・slot競合を確認
maximum_bytes_billed本profileは1クエリの上限1,000,000,000 bytes。月間予算上限ではない

総費用の比較例＝dbt実行SQL＋Data/Unit test＋Snapshot＋BIクエリ＋保存＋実行基盤/プラットフォーム。オンデマンドの処理バイトと、容量課金のslot/時間の観点を分けます。小さなサンプルの応答時間から本番費用を推定しません。

Viewを10段から1段へ変えるだけで、費用が10分の1になるとは限りません。逆に共通処理を複数Tableへ保存すると、各Tableのbuild費用と保存が増えます。Compiled SQL、BigQueryコンソールの処理バイト・実行計画・ジョブ実績を確認します。

require_partition_filterは大きいTableの誤読取防止に使える候補ですが、dbtのテストやMERGEも条件を必要とします。本サンプルでは初期値に含めていません。
