CHAPTER 01

MINとMAX：どこまで自動化するか

GitHub Actionsは、コードの検証、ビルド、クラウドへの反映、定期実行、結果保存を一つのワークフローにできます。この資料では、前のdbt教材を使って、最小実用構成と、品質・権限・証跡・運用を厚くした構成を比較します。

MIN／MAXはGitHubの公式プラン名ではありません。MAXは、本教材の目的に合わせた充実構成です。全機能を同時に有効化することや、サービス上限まで並列実行することを意味しません。

観点MIN：小さく始めるMAX：本番運用を厚くする
CIPython 3.12／parse／ローカル検算3.11・3.12のmatrix／同じ検算／固定ゲート
CDmainから手動で本番dbt build同一runのBigQuery検証→証跡照合→本番build
認証CDジョブのみOIDCstaging・productionのIDと権限を分離
品質SQLの構文と7事例のローカル検算実際の更新・物理削除・再実行を隔離環境で照合
運用短いtimeout／本番同時実行を制限CIキャンセル／pip cache／artifact／定期検証／Dependabot
費用PRはクラウドを使わないmain統合検証でBigQuery料金が発生
向く状況学習・小規模・構成を理解したい複数人開発・変更頻度が高い・監査証跡が必要

「最小」は安全性を削ることではありません。MINでもActionのSHA固定、read権限、OIDC、本番の実行条件、timeoutを入れています。導入するのはMINかMAXのどちらか一つです。

CHAPTER 02

CIとCDの基本構成

CIは変更の検証、CDは検証済み変更を対象環境へ反映する段階です。サンプルは本番実行を手動にするContinuous Deliveryです。mainへのpushだけで本番まで自動反映するContinuous Deploymentへ変更する場合は、監視と復旧条件も設計します。

YAML要素役割サンプルでの設定
on開始イベントpull_request／push main／workflow_dispatch
jobs／steps実行単位と手順CI・統合検証・本番を分ける
needs／if依存関係と実行条件前段成功かつmainの手動実行だけ本番へ
permissionsGitHubトークン権限contents: read、クラウドジョブだけid-token: write
environment環境単位の変数と保護staging／production
concurrency同時実行の制限本番は同じgroupを使用
CHAPTER 03

MINケース：最小の実用CI/CD

PR、mainへのpush、手動実行でCIを開始します。Python 3.12で依存を導入し、dbt parse、7件のCSV検算、3件の実行防止ガード検証を実施します。PRではGoogle Cloud認証を取得しません。

本番はActions画面のRun workflowでmainを選び、deployをtrueにした時だけ開始します。CI成功後にproduction環境の保護ルールを通り、OIDCでGoogle Cloudへ接続します。本番ではtag:baseのモデルとテストだけを実行し、seedとfull refreshを使いません。

メリット：読みやすく、クラウドなしでPR検証でき、導入コストが低いです。デメリット：BigQuery固有のSQL・IAM・実際の増分書込はCIで保証できません。依存の推移的解決もMAXほど固定していません。

MIN workflow全文
name: DBT MIN CI/CD
on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:
    inputs:
      deploy:
        description: 'Run production dbt build after CI (main only)'
        type: boolean
        default: false
permissions:
  contents: read
defaults:
  run:
    shell: bash
env:
  DBT_SEND_ANONYMOUS_USAGE_STATS: 'false'
jobs:
  ci:
    name: Offline CI
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-python@5fda3b95a4ea91299a34e894583c3862153e4b97 # v7.0.0
        with:
          python-version: '3.12'
      - name: Install dependencies
        run: python -m pip install -r requirements-offline.txt
      - name: Prepare local profile
        run: cp profiles/profiles.yml.example profiles/profiles.yml
      - name: Parse minimal and pattern projects without cloud access
        run: |
          dbt --no-send-anonymous-usage-stats --no-partial-parse parse --project-dir projects/minimal --profiles-dir profiles
          dbt --no-send-anonymous-usage-stats --no-partial-parse parse --project-dir projects/patterns --profiles-dir profiles --vars '{enable_patterns: true, enable_snapshots: true}'
      - name: Verify seven offline cases
        run: |
          python scripts/check_demo_offline.py
          python ci/test_guards.py
  production:
    needs: ci
    if: github.event_name == 'workflow_dispatch' && github.ref == 'refs/heads/main' && inputs.deploy
    runs-on: ubuntu-24.04
    timeout-minutes: 20
    environment: production
    concurrency:
      group: dbt-production
      cancel-in-progress: false
    permissions:
      contents: read
      id-token: write
    env:
      DBT_PROJECT: ${{ vars.GCP_PROJECT_ID }}
      DBT_DATASET: ${{ vars.DBT_PROD_DATASET }}
      DBT_RAW_PROJECT: ${{ vars.DBT_RAW_PROJECT_ID }}
      DBT_RAW_DATASET: ${{ vars.DBT_RAW_DATASET }}
      DBT_LOCATION: ${{ vars.BIGQUERY_LOCATION }}
      WIF_PROVIDER: ${{ vars.GCP_WIF_PROVIDER }}
      RUNTIME_SA: ${{ vars.GCP_SERVICE_ACCOUNT }}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-python@5fda3b95a4ea91299a34e894583c3862153e4b97 # v7.0.0
        with:
          python-version: '3.12'
      - name: Validate production settings
        run: python ci/preflight.py production
      - name: Install dependencies
        run: python -m pip install -r requirements.txt
      - uses: google-github-actions/auth@7c6bc770dae815cd3e89ee6cdf493a5fab2cc093 # v3
        with:
          project_id: ${{ env.DBT_PROJECT }}
          workload_identity_provider: ${{ env.WIF_PROVIDER }}
          service_account: ${{ env.RUNTIME_SA }}
          create_credentials_file: true
      - name: Prepare profile
        run: cp profiles/profiles.yml.example profiles/profiles.yml
      - name: Build and test production models (no seed or full refresh)
        run: |
          dbt --no-send-anonymous-usage-stats build --project-dir projects/patterns --profiles-dir profiles --select tag:base --exclude resource_type:seed --vars '{enable_patterns: false, enable_snapshots: false}'
      - name: Record deployed revision
        run: |
          printf '### Production build\nRevision: `%s`\n' "$GITHUB_SHA" >> "$GITHUB_STEP_SUMMARY"
CHAPTER 04

MAXケース：品質と運用を追加する

CIはPython 3.11／3.12を最大2並列で実行し、一つ失敗しても他方の結果を残します。quality-gateはmatrix全体が成功した時だけ通過する固定名のチェックです。必須ステータスチェックにはこのQuality gateを登録します。

mainのpush・手動実行・定期実行では、stagingで実際にBigQueryを操作します。runごとに別datasetを作り、初期データ→変更データ→同じ変更データの再実行を検証します。成功証跡を保存し、手動の本番ジョブがコミットSHA・run ID・attemptを照合してから反映します。

追加機能狙い代償・判断境界
matrix環境差を検出CI時間とrunner利用が増える
lock・cache依存バージョンの再現性／導入時間削減lockはLinux用・ハッシュ未固定。更新と再検証が必要
統合検証BigQuery・dbtの実動作を検証IAM設定とクラウド料金が必要
artifactmanifest・実行結果・同一コミット証跡保存料金とデータ露出範囲を管理
定期検証変更がなくても依存や接続の破損を検知サンプルは毎日。不要ならschedule削除
DependabotAction・pip更新をPRでレビュー自動マージは含めない

name: DBT MAX CI/CD
on:
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: '15 16 * * *' # UTC 16:15 = JST 01:15 (scheduled execution is not an SLA)
  workflow_dispatch:
    inputs:
      deploy:
        description: 'Promote tested main revision to production'
        type: boolean
        default: false
permissions:
  contents: read
defaults:
  run:
    shell: bash

      cancel-in-progress: true
    steps:

        with:
          persist-credentials: false
      - uses: actions/setup-python@5fda3b95a4ea91299a34e894583c3862153e4b97 # v7.0.0
        with:
          python-version: ${{ matrix.python }}
          cache: pip
          cache-dependency-path: requirements-linux.lock.txt
      - name: Install dependencies
        run: python -m pip install -r requirements-linux.lock.txt
      - name: Prepare local profile
        run: cp profiles/profiles.yml.example profiles/profiles.yml
      - name: Parse minimal and pattern projects without cloud access
        run: |
          dbt --no-send-anonymous-usage-stats --no-partial-parse parse --project-dir projects/minimal --profiles-dir profiles
          dbt --no-send-anonymous-usage-stats --no-partial-parse parse --project-dir projects/patterns --profiles-dir profiles --vars '{enable_patterns: true, enable_snapshots: true}'
      - name: Verify seven offline cases
        run: |
          python scripts/check_demo_offline.py
          python ci/test_guards.py
      - name: Upload parse evidence only
        if: always()
        uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
        with:
          name: parse-python-${{ matrix.python }}-${{ github.run_id }}-${{ github.run_attempt }}
          path: |
            projects/minimal/target/manifest.json
            projects/patterns/target/manifest.json
          retention-days: 3
          if-no-files-found: ignore
  quality-gate:
    name: Quality gate
    needs: ci
    if: always()
    runs-on: ubuntu-24.04
    timeout-minutes: 2
    env:
      CI_RESULT: ${{ needs.ci.result }}
    steps:
      - name: Require all matrix cases to succeed
        run: test "$CI_RESULT" = success
  integration:
    needs: quality-gate
    if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    environment: staging
    concurrency:
      group: dbt-staging
      cancel-in-progress: false
    permissions:
      contents: read
      id-token: write
    env:
      DBT_PROJECT: ${{ vars.GCP_PROJECT_ID }}
      DBT_DATASET: dbt_ci_${{ github.run_id }}_${{ github.run_attempt }}
      DBT_RAW_PROJECT: ${{ vars.GCP_PROJECT_ID }}
      DBT_RAW_DATASET: dbt_ci_${{ github.run_id }}_${{ github.run_attempt }}
      DBT_LOCATION: ${{ vars.BIGQUERY_LOCATION }}
      WIF_PROVIDER: ${{ vars.GCP_WIF_PROVIDER }}
      RUNTIME_SA: ${{ vars.GCP_SERVICE_ACCOUNT }}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-python@5fda3b95a4ea91299a34e894583c3862153e4b97 # v7.0.0

          dbt --no-send-anonymous-usage-stats build --project-dir projects/patterns --profiles-dir profiles --exclude resource_type:seed --vars '{enable_patterns: true, enable_snapshots: true}'

CHAPTER 05

図解：PRとクラウドの権限境界

PRコードは変更者が制御します。PRではcontents: readのローカル検証だけを実行し、Google Cloud認証を取得する統合検証はmainへマージされた変更に限定します。mainの保護とワークフロー変更のレビューがこの境界を支えます。

pull_request_targetでPRのコードをcheckoutして権限付き実行する構成は採用しません。PRタイトルやブランチ名をrunのシェルに直接埋め込まず、必要ならenv経由で渡して引用します。キャッシュは高速化用であり、デプロイ済み成果物の証明には使いません。

Actionは40桁のコミットSHAで固定しました。依存更新時はDependabotのPRと差分をレビューします。SHA固定はAction自体の安全性を自動保証するものではありません。

CHAPTER 06

導入手順とファイル構成

ZIPを展開し、sample-repositoryをGitHubリポジトリのルートに置きます。variants/minまたはvariants/maxの.github/workflows/dbt-ci-cd.ymlを、リポジトリの.github/workflowsへコピーします。MAXではdependabot.ymlもコピーします。二つのworkflowを同時に有効にすると、同じモデルが重複実行されるため、必ず一方だけ選びます。

  04-github-actions-ci-cd-guide.html
  variants/min/.github/workflows/dbt-ci-cd.yml
  variants/max/.github/workflows/dbt-ci-cd.yml
  variants/max/.github/dependabot.yml
  sample-repository/
    ci/preflight.py / staging.py / check_evidence.py / test_guards.py
    scripts/check_demo_offline.py
    projects/minimal/ / projects/patterns/

  1. MIN／MAXのどちらかをコピーし、まずPRのクラウドなしCIを通します。
  2. GitHub Settingsで環境と変数、mainの保護、workflow変更レビューを設定します。
  3. Google Cloud側でWIF、サービスアカウント、BigQuery IAMを設定します。
  4. MAXはstagingの統合検証を先に通します。MINは本番相当の検証用環境で手動確認してください。
  5. 本番のrawデータと出力datasetを準備し、mainからdeploy=trueの手動実行を開始します。

サンプルは前のdbt教材の架空注文スキーマ専用です。既存の任意のdbtプロジェクトを、そのままこの本番コマンドで扱えるわけではありません。実運用ではモデル、テスト、raw sourceを自社の構成へ置き換えます。

CHAPTER 07

GitHub側で必要な設定

YAMLのenvironment: productionだけでは承認を有効にできません。Settings → Environmentsでproductionを事前作成し、必要なレビュアー、自己承認禁止、デプロイ可能ブランチmainを設定します。stagingはmainだけに制限します。

環境の保護機能はプランと公開／非公開で利用範囲が変わります。利用できない場合、この教材と同じ承認保証は成立しません。組織の利用プランか別の承認経路を確認してください。

Environment variable設定先値・目的
GCP_PROJECT_IDstaging／productionBigQueryジョブのproject ID。環境ごとに別project推奨
BIGQUERY_LOCATION両環境例：asia-northeast1。rawと出力のlocationを合わせる
GCP_WIF_PROVIDER両環境projects/数値/locations/global/workloadIdentityPools/…/providers/…
GCP_SERVICE_ACCOUNT両環境環境ごとに専用のSAメール
DBT_PROD_DATASETproduction出力先。例analytics_prod。事前作成
DBT_RAW_PROJECT_IDproductionraw_orders／raw_customers／raw_eventsのproject
DBT_RAW_DATASETproductionraw source dataset。事前ロード

mainのRulesetまたはBranch protectionでは、PRを必須にし、MAXのQuality gate（MINはci）を必須チェックにします。実際に一度CIを実行して表示されたチェック名を登録してください。workflow／ciスクリプト／本番モデルの変更には担当者レビューを要求します。

# CODEOWNERS例：実在するGitHubチームに置き換える
/.github/ @your-org/platform-team
/ci/ @your-org/platform-team
/projects/ @your-org/data-team

CODEOWNERSファイルを置くだけではレビュー必須にはなりません。ブランチ保護のRequire review from Code Ownersも設定します。サンプルのプレースホルダーは自動コピーしません。

CHAPTER 08

Google Cloud認証とIAM

本教材はGoogle Cloudサービスアカウント鍵JSONをGitHubに保存せず、GitHub OIDC → Workload Identity Federation → サービスアカウントの構成です。id-token: writeはOIDCトークン取得用であり、BigQuery権限はGoogle Cloud IAMで別途制御します。

主体・対象権限の考え方適用範囲
GitHubのWIF principal対象SAへのroles/iam.workloadIdentityUser対象リポジトリ・main・environmentに限定
production SAroles/bigquery.jobUserクエリ実行project
production SAroles/bigquery.dataViewerraw datasetだけ
production SAroles/bigquery.dataEditor出力datasetだけ
staging SAjobUser＋dataset作成・管理に必要な権限専用の検証project。dataEditorのproject付与は広いため専用projectへ隔離

WIFのattribute mappingとconditionでrepository_id／repository_owner_idなどの不変ID、ref、environmentを制限します。トークンのsub形式にはリポジトリ作成・名称変更時期による差があるため、古いrepo:owner/name:…形式を決め打ちしません。実際のclaimと公式資料で設定します。

gha-creds-*.jsonは一時認証ファイルです。gitignoreし、artifactや配布ZIPに含めません。stagingとproductionで同じ広い権限のSAを共有しない設計にしてください。

CHAPTER 09

BigQueryで何を検証するか

MAXはrunごとにdbt_ci_RUNID_ATTEMPTとその_snapshots datasetを作ります。dataset名とrun IDの一致をコードで検査し、cleanupが本番datasetへ作用しないようにします。テーブルに24時間の既定有効期限を設定し、最後にdatasetを削除します。

照合項目phase2後の期待値示している挙動
全件martのpaid売上349修正・キャンセル・物理削除の反映
MERGEのpaid売上469通常のupsertでは消えた注文120が残るという既知の制約
partition置換のpaid売上349指定日のパーティション再作成
不変イベント件数4再実行で件数が増えない
現在有効な顧客snapshot3同じ入力の再実行で現行行が増えない

469を成功条件にしているのは、教材のMERGE削除問題を再現するためです。本番の正しい売上として容認する意味ではありません。本番用ゲートでは業務上の正しい期待値と削除伝播方式に置き換えてください。

ローカル7件はDuckDBでSELECT相当を検算するもので、BigQueryの実行・権限・増分materializationを保証しません。BigQuery固有の検証はMAXのintegrationジョブで初めて行われます。

CHAPTER 10

本番の直列化・失敗・復旧

本番とstagingには固定のconcurrency groupとcancel-in-progress: falseを設定します。実行中の本番buildを新しいrunのために中断しません。ただし既定の待機枠では、古いpendingが新しいpendingに置換されることがあり、dispatch順の完全な実行保証ではありません。

CIにはcancel-in-progress: trueを使い、同じrefの古い検証を中止します。全体workflowのキャンセルにすると本番まで止まり得るため、サンプルではCIジョブ単位にしています。

失敗地点対応
PR CI修正してPRを更新。クラウド作業なし
integrationmainの同じコミットで再実行し、BigQuery・dbtログを確認。異なるattemptの証跡は本番に流用しない
本番dbt buildrun_resultsとBigQueryジョブを調べ、部分反映を確認してから対象モデルを再実行
cleanup専用検証projectで残存datasetを監視し、管理者が確認して削除

dbt build全体は一つのトランザクションではありません。後半のテスト失敗でも前半のテーブル更新が残ることがあります。Gitの旧コミットへ戻すだけではデータは戻りません。停止、影響確認、旧SQL再buildまたはバックアップ復元の手順を別途整備します。自動ロールバックは本サンプルに含みません。

always()でも強制終了時にはcleanupが動かない場合があります。24時間TTLはテーブル用で、dataset自体の自動削除ではありません。runnerの中断が既に開始されたクラウドジョブを必ず停止する保証もありません。

CHAPTER 11

費用対効果と実行速度

最適化の順序は、不要なrunを減らす、必要な対象だけを検証する、再利用できる導入結果をcacheする、適切な並列度を選ぶ、最後にrunnerを増強する、です。MINはPRでBigQueryを使わず、MAXの統合検証もmainに限定しています。

設定効果注意点
max-parallel: 2matrixの並列度を抑える並列化は待ち時間を短縮しても総利用分を減らすとは限らない
timeout-minutes異常な長時間実行を制限正常runの計測後に調整
pip cache依存download時間を短縮キーをlockファイルに連動。認証情報を保存しない
artifact保存3日／7日証跡を必要期間だけ保存組織の監査要件に合わせる
BigQuery最大読取1GB／クエリ過大なクエリを失敗させる1run全体の総額上限ではない。クエリ数・slot・別サービスも考慮
日次schedule継続的な接続検証JST01:15相当。遅延やスキップがあり、厳密な時刻保証ではない

サンプルではpathsフィルターを入れていません。必須チェックを付けたworkflow自体をpaths条件で開始しないと、チェックがpendingのままになる場合があるためです。大規模monorepoでは、常に起動する判定ジョブと必須ゲートを残し、必要な検証ジョブだけを条件分岐します。

概算は、runnerのジョブ利用量＋artifact/cacheの保存利用量＋BigQueryの実行量です。具体的単価と無料枠はプラン・runner・課金方式で変わるため、固定価格例を保証せず、実際のBillingとクエリ統計で測定します。

CHAPTER 13

GitHubの上限とMAXの違い

利用上限はGitHubプランとrunner種別で変わります。現在の公式資料では、matrixで生成できるジョブは1workflowあたり最大256、GitHub hostedの1ジョブ実行時間は最大6時間です。これはサービス上限であり、推奨設定値ではありません。本教材は2並列・短いtimeoutに抑えています。

予算・利用枠・保存容量・API制限・クラウド側quotaも別々に存在します。self-hosted runnerを使う場合は、運用、更新、ネットワーク隔離、PRからの侵害、残留ファイルを扱う責任が増えます。サンプルはGitHub hosted Ubuntu 24.04です。
