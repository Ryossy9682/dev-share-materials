# P05 更新時刻＋MERGEによる差分反映

場面：注文金額・状態が更新され、信頼できるupdated_atと主キーがある。

サンプル：`projects/patterns/models/patterns/p05_orders_merge.sql`

| 比較 | 内容 |
|---|---|
| メリット | 過去キーの修正と再実行に対応できる。更新対象を限定できる。 |
| デメリット | 物理削除は残る。lookbackより古い到着は拾えない。宛先MERGEの読取も必要。 |

確認例：phase2の金額・状態変更は反映しますが、注文6の120が残り、paid合計469になります。現在の正しい349との差分を確認します。

判断上の注意：unique_keyはDB制約の自動保証ではありません。宛先を直近日だけに絞るincremental_predicatesで過去キーが不一致になると、重複を作ることがあります。

事例は架空データに基づく教材です。実行手順は`docs/01-quickstart.md`、変更シナリオは`docs/02-change-scenarios.md`を参照してください。
