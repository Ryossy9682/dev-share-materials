# P10 テストと契約による公開品質の担保

場面：売上指標を複数部署へ配布し、変更時に壊れた列や計算を検出したい。

サンプル：`projects/patterns/models/schema.yml`

| 比較 | 内容 |
|---|---|
| メリット | キー・型・業務整合・境界のチェックをコード化できる。 |
| デメリット | テストもクエリ費用・実行時間を使う。合格は業務の全意味を保証しない。 |

確認例：Data tests、Unit test、Contract、tests/assert_sales_total_matches_base.sqlを実行対象として確認します。

判断上の注意：Contractは列名と型、Data testは既存データの条件、Unit testはfixtureに対する処理です。Freshnessは別の観点です。build失敗でも更新済みモデルが残る可能性があります。

事例は架空データに基づく教材です。実行手順は`docs/01-quickstart.md`、変更シナリオは`docs/02-change-scenarios.md`を参照してください。

出典： https://docs.getdbt.com/docs/build/data-tests
