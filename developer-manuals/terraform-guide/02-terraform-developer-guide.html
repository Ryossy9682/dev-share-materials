MANUAL 02 / 01

開発者が最初に読むTerraform

設定を書く → 差分を確認する → 反映する → stateを管理する

Terraformは、クラウドの構成をコードで宣言し、現在の状態との差分を反映するためのツールです。本書はGoogle CloudのCloud Runを題材に、最初の実行からチーム運用までを扱います。

必須の設定例役割
minimal：最小構成1つのmain.tfで基本のprovider・resource・variable・outputを学ぶ
detailed：詳細設定設定を観点別に分け、認証、費用、ネットワーク、監視、保護を管理する

2つは同じ関数イメージを使う別サービスです。詳細版の方が速い・安いと決まっているわけではありません。設定の明示範囲と運用方法を比べる教材です。

前のCloud Run functionsマニュアルのHTTP関数をコンテナにし、Cloud Runサービスとして管理します。Terraform自身は本例のPythonソースをビルドしません。既存functionsへの移行をそのまま実行する構成でもありません。

対象：基本的なコマンド操作ができる開発者。PowerShellの例を掲載しています。サンプルはTerraform 1.9以上2.0未満、Google provider 7.10系を対象にし、確認したバージョンを固定します。最新版であるという意味ではありません。

出典：[01] Terraformの基本実習, [07] モジュール, [17] Cloud Runリソース設定, [18] コンテナ配置

MANUAL 02 / 03

02 開発の流れ

反映前のplan確認を、日常の開発フローに組み込みます。

コマンド目的
initprovider・module・backendの初期化
fmt / validate整形 / 設定とprovider schemaの整合性確認
planstate・実リソースと設定を比較する。原則、実物を変更しない
apply計画を反映する。クラウドの作成・更新・削除が起こる
output / plan確認用値の取得 / 変更が残っていないか確認
terraform init
terraform fmt -check
terraform validate
terraform plan -out="change.tfplan"
terraform show "change.tfplan"
terraform apply "change.tfplan"
terraform plan

保存済みplanをapplyに渡す場合、追加の確認プロンプトなしで反映されます。showでレビューしたplanを使い、古いplanや別環境のplanを使わない運用にします。validateの成功だけでは権限・クォータ・実際のAPI受付まで保証できません。

出典：[02] init, [03] validate, [04] plan, [05] apply

03 ファイル・変数・依存関係

ファイルは見通しのために分けます。作成順序は参照関係で決まります。

詳細版のファイル読む観点
versions.tf / .terraform.lock.hcl使用範囲の指定 / 選択したproviderとチェックサム
backend.tf / backend.dev.hclstate保存方式 / 保存先とprefix
variables.tf / terraform.tfvars入力の型・初期値・検証 / 環境ごとの実値
main.tf / monitoring.tf / outputs.tf本体 / 監視 / 利用者が確認する出力
variable "cpu" {
  type    = string
  default = "1"
}
# resourceの中からvar.cpuを参照します。

同じフォルダーの.tfはまとめて1つの構成になります。main.tf、iam.tf等の名前は処理順を意味しません。SAのemailをCloud Runで参照すれば、その参照が依存関係になります。API有効化等、参照だけでは表せない依存にdepends_onを使います。

tfvarsは値、tfは構成です。backendの設定はinitで使うため、通常の入力変数をそのまま参照できません。必要以上にmoduleを増やさず、複数の呼び出し元で再利用するまとまりができた時点で切り出します。

04 開発環境と認証を準備する

Terraformの実行者、関数の実行者、呼び出す人は別の主体です。

terraform version
gcloud auth login
gcloud auth application-default login
gcloud auth application-default set-quota-project YOUR_PROJECT_ID

gcloudの認証とTerraform providerのADCは別設定です。サンプルは鍵JSONをHCLへ書く方法を使いません。CIでは短期認証やWorkload Identity Federationを検討します。

主体権限を確認する対象
Terraform実行者Cloud Run作成・更新、実行SAのactAs、API/IAM/監視等の管理
ビルド用SAソース、Cloud Build、Artifact Registry、ログ
関数の実行用SA関数がアクセスするデータ・Secret
サービスの呼び出し元Cloud Run Invoker
state利用者GCS backendのバケット内オブジェクト操作

実際の必要権限は、作るリソースと組織ポリシーで決まります。通常運用者へOwnerを一律に与えず、設定担当者と操作単位で確認します。詳細な事前準備とビルドコマンドはdocs/01-prerequisites.mdに掲載しています。

06 最小構成版を実行する

最初は1ファイルを読んで、必要な要素の関係を把握します。

samples/minimalではRun API、実行SA、イメージを事前に用意します。IAM認証は有効ですが、呼び出しメンバーの追加は別手順です。CPU・メモリ等の既定値を多く使うため、費用設定は別途確認します。

cd samples/minimal
Copy-Item terraform.tfvars.example terraform.tfvars
# project_id、image、runtime_service_accountを編集

terraform validate
terraform test
terraform plan -out="change.tfplan"
terraform show "change.tfplan"
terraform apply "change.tfplan"
最小構成のmain.tf全文
terraform {
  required_version = ">= 1.9.0, < 2.0.0"
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 7.10.0"
    }
  }
}
provider "google" {
  project = var.project_id
  region  = var.region
}

# 学習用：API、SA、イメージは事前に用意します。
variable "project_id" { type = string }
variable "region" {
  type    = string
  default = "asia-northeast1"
}
variable "service_name" {
  type    = string
  default = "tf-hello-minimal"
}
variable "image" { type = string }
variable "runtime_service_account" { type = string }

resource "google_cloud_run_v2_service" "app" {
  name                 = var.service_name
  location             = var.region
  deletion_protection  = false
  ingress              = "INGRESS_TRAFFIC_ALL"
  invoker_iam_disabled = false
  template {
    service_account = var.runtime_service_account
    containers {
      image = var.image
    }
  }
}
output "service_url" { value = google_cloud_run_v2_service.app.uri }

terraform.tfvars.exampleはそのままでは実行用の値になりません。.exampleを外したファイルへコピーして編集します。ローカルstateを紛失せず、学習後の削除は対象範囲をplanで確認します。

07 詳細設定版を実行する

運用上の重要な項目を明示し、環境差を変数で表します。

GCSのstateバケットを先に用意します。samples/bootstrap-stateは作成用の補助構成です。詳細版のbackend.dev.hclへbucketと環境別prefixを書き、initします。

cd samples/detailed

# bucket、prefix、project、image、invoker_members等を編集

terraform validate

terraform show "change.tfplan"

詳細構成のmain.tf全文
locals {
  apis       = toset(["run.googleapis.com", "iam.googleapis.com", "secretmanager.googleapis.com", "monitoring.googleapis.com"])
  normal_env = merge(var.env, { APP_ENV = var.environment, THREADS = tostring(var.concurrency) })
}
# この構成を削除しても共有プロジェクトのAPIを無効化しません。
resource "google_project_service" "api" {
  for_each           = local.apis
  project            = var.project_id
  service            = each.key
  disable_on_destroy = false
}
resource "google_service_account" "runtime" {
  project      = var.project_id
  account_id   = var.runtime_account_id
  display_name = "Cloud Run runtime (${var.environment})"
  depends_on   = [google_project_service.api]
}
# secret_envに指定したSecretだけに読み取り権限を付けます。
resource "google_secret_manager_secret_iam_member" "runtime" {
  for_each  = toset([for s in values(var.secret_env) : s.secret_id])
  project   = var.project_id
  secret_id = each.key
  role      = "roles/secretmanager.secretAccessor"
  member    = "serviceAccount:${google_service_account.runtime.email}"
}
resource "google_cloud_run_v2_service" "app" {
  project              = var.project_id
  name                 = var.service_name
  location             = var.region
  deletion_protection  = var.deletion_protection
  ingress              = var.ingress
  invoker_iam_disabled = false
  labels = {
    environment = var.environment
    managed_by  = "terraform"
  }
  scaling {
    min_instance_count = var.min_instances
    max_instance_count = var.max_instances
  }
  template {
    service_account                  = google_service_account.runtime.email
    timeout                          = "${var.timeout_seconds}s"
    execution_environment            = "EXECUTION_ENVIRONMENT_GEN2"
    max_instance_request_concurrency = var.concurrency
    session_affinity                 = false
    containers {
      image = var.image
      ports { container_port = 8080 }
      resources {
        limits            = { cpu = var.cpu, memory = var.memory }
        cpu_idle          = true # リクエストベース課金
        startup_cpu_boost = var.startup_cpu_boost
      }
      dynamic "env" {
        for_each = local.normal_env
        content {
          name  = env.key
          value = env.value
        }
      }
      dynamic "env" {
        for_each = var.secret_env
        content {
          name = env.key
          value_source {
            secret_key_ref {
              secret  = env.value.secret_id
              version = env.value.version
            }
          }
        }
      }
      startup_probe {
        initial_delay_seconds = 0
        timeout_seconds       = 2
        period_seconds        = 5
        failure_threshold     = 12
        http_get { path = "/" }
      }
      # liveness probeは本例では使いません（課金方式との互換性を別途確認）。
    }
    dynamic "vpc_access" {
      for_each = var.vpc == null ? [] : [var.vpc]
      content {
        egress = vpc_access.value.egress
        network_interfaces {
          network    = vpc_access.value.network
          subnetwork = vpc_access.value.subnetwork
        }
      }
    }
  }
  traffic {
    type    = "TRAFFIC_TARGET_ALLOCATION_TYPE_LATEST"
    percent = 100
  }
  lifecycle {
    prevent_destroy = true # 解除にはこの定数をfalseへ変更します。
  }
  depends_on = [google_project_service.api, google_secret_manager_secret_iam_member.runtime]
}
# member型を使用して、他チームの同じロールのメンバーを一括上書きしません。
resource "google_cloud_run_v2_service_iam_member" "invoker" {
  for_each = var.invoker_members
  project  = var.project_id
  location = var.region
  name     = google_cloud_run_v2_service.app.name
  role     = "roles/run.invoker"
  member   = each.key
}

08 2種類の設定を比較する

項目が増えた理由と、どこまで管理するかを比較します。

観点minimaldetailed
ファイル構成main.tfに集約観点別に分割
stateローカルGCS。事前にバケットを用意

09 stateとGCS backendを理解する

stateはキャッシュではなく、継続管理に必要な対応表です。

ローカルstateは一人での学習には扱いやすいですが、チームで個別にコピーすると管理が分裂します。GCS backendは共有とロックに対応し、バケットのバージョニングを有効にして復旧に備えます。

管理ルール目的
stateをGitへ入れない機密・内部情報を保護し、実行者だけにアクセスを限定
環境ごとにprefix等を分けるdev/stg/prodの管理対象を分離
.terraform.lock.hclをGitへ入れるproviderの選択を再現する。stateのロックとは別物
stateバケットを先に作るbackend初期化時点で保存先を利用できるようにする

保存先を変えるときはstateをバックアップし、terraform init -migrate-stateで移行します。-reconfigureは移行の代わりではありません。ロックがある場合、実行中の処理を確認してから対処します。

10 IAM・Secret・ネットワーク

認証、アクセス経路、実行権限を別の設定として考えます。

設定意味と確認事項
invoker_iam_disabled=false呼び出し時のIAMチェックを有効にする
invoker_membersuser/group/serviceAccountだけ追加。allUsersは入力検証で拒否
ingress到達できるネットワーク経路。ALLでも認証が不要になるわけではない
runtime SA関数がデータやSecretへアクセスするID
secret_env既存SecretのIDと数字バージョンを参照。機密値本体はTerraformで作らない
vpc既存ネットワークと同リージョンのサブネットを使用

member型のIAMリソースは特定の主体を追加します。binding/policy型は管理範囲が広いため、別の設定が管理するメンバーを消す可能性も含めて設計します。本例はmember型を使いますが、同じIAMを別stateと二重管理しないルールは必要です。

sensitive=trueは表示を隠す指定で、通常のstateへ保存しない保証ではありません。envへパスワードを直書きしないでください。VPCのALL_TRAFFICを選ぶと、インターネット到達にCloud NAT等が必要になる場合があります。VPC接続がGoogle APIへのIAM権限を付けることもありません。

11 チーム開発とCI

planをレビューできる状態にし、適用先・実行者・stateを明確にします。

state利用権限と構成管理権限は分けて検討します。planファイルも機密を含み得るため、公開ログや誰でも取れる成果物へ置きません。実行を直列化し、stateロックを無効にして競合を回避しようとしない運用にします。

providerの更新は専用変更としてinit -upgradeを行い、ロック差分とplanを確認します。初期化ごとに無条件で最新へ追従しません。mockテストはクラウドAPIの実動作や権限を保証しないため、開発環境のapplyと疎通確認を別に実施します。

MANUAL 02 / 13

12 コストを最適化する設定

Terraformは費用を決定する設定を管理します。applyの速さと実行費用は別です。

費用に影響する項目本書の基準と調整方法
cpu / memory詳細版は1 CPU / 512Mi。時間・成功率・ピークと合わせて比較
concurrency / THREADS8を基準に、I/O待ち・CPU集中・同時メモリを測る
min_instances / max_instances0 / 3。初回遅延と待機費用、負荷時の成功率を比べる
cpu_idle / startup_cpu_boostリクエストベース / false。頻度・起動時間に応じて比較
Secret / VPC / Monitoring / state依存リソース・通信・保存も総額へ含める

同じ入力・同じ負荷で、平均/p95応答時間、成功した業務件数、再試行、課金対象時間、外部API費用を比較します。成功1件の費用＝期間総費用÷重複を除いた成功件数、という指標を使う設計例です。詳細版の固定値が最安とは限りません。

最大インスタンス数は厳密な支出上限ではありません。stateの過去バージョン、Artifact Registry、Cloud Build、通信も費用を確認します。Terraform CLIのplanだけを速くしても、配置された関数1回の費用が下がるわけではありません。

出典：[21] 費用最適化, [22] Cloud Run料金, [23] 同時実行

13 import・変更・削除を扱う

対象リソースと管理範囲を確認し、置換や削除を見落とさないようにします。

planの+は作成、~は変更、-は削除、-/+等は置換を表します。置換は停止や再作成があり得るため、名前・場所・接続・データへの影響を確認します。apply中に失敗した場合も、作成済みリソースが残ることがあります。

import {
  to = google_cloud_run_v2_service.app
  id = "projects/PROJECT_ID/locations/asia-northeast1/services/SERVICE_NAME"
}

importは既存リソースをstateへ関連付けるための例です。設定コードを実物へ合わせ、planで予期しない差分を解消します。最小版から詳細版へ同じ名前をコピーするだけで移行したことにはなりません。既存functionsの管理方式も先に確認します。

詳細版の削除手順必要な操作
1：対象確認プロジェクト・state・サービスを確認する
2：Terraform側保護を解除main.tfのprevent_destroy定数をfalseへ変更
3：provider側保護を解除deletion_protection=falseを通常のapplyで反映
4：削除planを確認plan -destroy -out=destroy.tfplan → show
5：反映確認したdestroy.tfplanをapply

stateバケットはこの詳細版の削除対象ではありません。APIも無効化しない設定です。イメージ、Secret本体、VPC、通知チャネルは残るので、別途所有者と整理します。prevent_destroyはコードを消しても保護が残る保証ではなく、IAM・運用の代わりにはなりません。

MANUAL 02 / 15

14 よくある問題と完了条件

エラーを見たときは、構文・認証・API・state・実サービスの順に切り分けます。

症状確認する内容
initの失敗ネットワーク、provider取得、backend bucket、ADC、state権限
validateの失敗providerバージョン、属性名、型、参照、dynamicの構造
planの403ADCの実行主体、API有効化、IAM、組織ポリシー
serviceが起動しないイメージ、8080、startup probe、実行SA、Secret参照
差分が毎回出る管理の二重化、コンソール変更、タグ更新、既定値、ignore_changesの必要性
stateロック実行中の処理とロック所有者。即force-unlockしない

ignore_changesで全部の差分を隠すと、設定が実物を管理できなくなります。別ツールが管理する範囲だけを設計上の理由とともに限定します。

完了条件：fmt/validate、mockテスト、planレビュー、開発環境のapply、IAM付き疎通、ログ、再plan、state保存・復旧方法、削除範囲の説明がそろうこと。本成果物の検証実績と未実施範囲はdocs/04-validation.mdに記載します。
