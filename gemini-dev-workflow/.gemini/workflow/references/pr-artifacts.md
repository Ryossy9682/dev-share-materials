# PR添付用資料

PR作成直前にgdw-deliverが`<案件ルート>/pr/`へ以下を生成・更新する。ソースの工程MDはそのまま保持し、同一工程の修正は正本へ反映してから再出力する。

| ファイル | 用途 |
|---|---|
| pr-summary.md | PR本文へ貼る短い変更概要・目的・検証・残る制約・添付案内 |
| pr-report.md | レビュアー向けの整理された統合報告。入口の目次と各工程への相対リンク |
| stages/ | 最新の工程MD、必要なdesign/詳細、更新履歴を含む可搬コピー |
| evidence/ | 添付に必要な検証証拠のみ。個人情報・秘密を除いたコピー |
| manifest.json | branch/base/head SHA・要件版・ファイルのSHA-256・生成日時 |
| feature.xxx-review.zip | 上記を束ねたPR添付用ZIP。自分自身をZIPに含めない |

pr-report.mdは「変更の目的と範囲」「要件・設計・実装の対応」「検証結果」「リリース準備と未実施事項」「更新履歴への案内」の5項目以内でまとめる。工程の長い履歴はstagesへ分離する。見出し、表、用語、時刻、判定表記を統一し、未解決・未検証を隠さない。Markdown表示で表やリンクを確認する。ローカル絶対パスは可搬な相対リンクへ置換する。最新内容と履歴を取り違えない。

正本のハッシュとコピーのハッシュは区別し、匿名化・パス修正したコピーに元のハッシュを流用しない。マニフェストは自己ハッシュとZIP自身のハッシュを含めず、ZIPのハッシュは00-index.mdに記録する。関連ファイルが変われば添付一式を再生成する。

PR base=develop、head=作業ブランチを確認する。/tmpのパスは他人から参照できるURLではない。利用中サービスの実際の添付機能でZIPを添付するか、ユーザーが利用できるZIPを出力する。添付APIが使えなければ作成済みファイルを提示し「添付待ち」と記録する。添付済みURLを捏造しない。PR作成・添付の権限と公開範囲を守り、マージしない。

PR作成時点で本番未承認/外部マージ待ちなら、その状態を明記する。後続工程を成功済みにしない。実行された本番工程の結果はrelease.mdに更新し、必要ならPR添付を更新する。

## 更新順と循環の防止

release.md・delivery.mdの技術的な準備内容を先に確定→PR本文案と報告書→ZIP作成・確認→PR作成/添付→PR・添付URL等の管理情報をdelivery.mdと00-index.mdへ記録、の順に進める。

ZIPには00-index.md、state.json、handoff.md、resume.mdを含めない。delivery.mdの可搬コピーから「添付管理情報」（ZIPハッシュ・アップロードURL・アップロード日時）を除く。これらの管理情報だけの更新は再生成対象にしない。技術的な要件/設計/実装/検証/リリース内容が変わった場合だけ新しいZIPを生成する。これによりZIPのハッシュや添付URLが自分自身の内容へ戻る循環を防ぐ。sourceハッシュはコピー直前の値として区別する。
