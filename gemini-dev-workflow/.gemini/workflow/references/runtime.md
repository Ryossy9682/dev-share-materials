# 案件の機械検査と復旧

この規約は全案件スキルの固定入力。configureは初期設定規約を使い、案件ルートが完成した後に適用する。Gemini CLIのコマンドは操作入口であり、承認や合格判定そのものではない。

## 正本と検査用データ

工程MDは引き続き人が読む正本。`gate.json`は要件ID・受入条件・対応ファイル・承認参照・レビュー・テスト結果・依存関係を記録する検査用索引。元資料とのハッシュ一致を検査し、GeminiがPASSという文字だけを書いて工程を完了させない。

`gate.json`を案件進行の唯一の正本とし、init後はそのstage/completedを使用する。state.jsonは案件識別・担当・資料一覧等の補助情報として保持し、旧stage/status/next_actionは進行判断に使わない。

`state.json`、`gate.json`、工程MD、実コード、実行ログを読む。要件定義の初回準備でbranch.mdと案件ルートを作った後にinitする。既存案件は移行に必要な記録が揃うまでBLOCKEDとし、足りない根拠を推測で埋めない。ランタイムのコマンド一覧・JSONの項目は実装ヘルプとgate.jsonひな型を参照する。

```sh
python .gemini/workflow/runtime/gdw.py --help
```

要件定義のIDはREQ-IDとAC-IDを一意にする。構造化索引へ転記しただけでは要件充足を証明しない。独立レビューで全IDと正本の内容を照合する。

## 各工程の実行

1. statusで現在工程と停止理由を確認する。原本やコードを更新した場合はimpactを実行する。Notion原本は再取得し、未取得は未確認として停止する。
2. スキルの固定入力と、この規約で追加した機械判定用ファイルを読み、工程の作業を行う。
3. 成果物・依存する入力・対象コードのハッシュ、要件対応、実行結果を登録する。承認は実際の発言をapproval.mdへ記録して紐付ける。レビューは独立した担当の原文を保持する。
4. checkの合格後、advanceで進行する。失敗時は判定JSONと停止理由を読み、原因工程へ差し戻す。gate.jsonの進行状態を手編集して迂回しない。完了ごとに永続チェックポイントを保存し、保存失敗を無視して次工程へ進まない。
5. statusの内容から現在工程・完了工程・停止理由・次の操作だけを簡潔に利用者へ示す。

実行記録はrunで非本番コマンドをargvとして実行して作る。コマンド、cwd、対象ハッシュ、終了コードとログを保存する。カバレッジレポートは使用した計測器の生データから転記・変換し、原本もハッシュ付きで保持する。UTと結合テストの記録を混ぜない。現行ランタイムはcoverage.py互換JSON（行・分岐の実行/未実行一覧）を受け付ける。他の計測器は初期設定で変換コマンドと対応確認を用意し、未対応のまま合格にしない。実行・変異・本番承認のsource_hashは、source_mapで根拠付きの対象外となったファイルだけを除いて算出する。

## 資料変更とやり直し

資料やコードのハッシュと、どの工程がそれを読むかを登録する。変更した入力に直接依存する工程と、その後続の依存工程だけをSTALEとする。新規ファイル・新しいNotion子ページは未分類とし、関連付けまたは対象外の根拠を決めるまで完了にしない。無関係な資料変更で全工程をやり直さないため、対象外判断と依存関係自体もレビューする。

初期設定の更新はproject-setup.mdに従う。案件への影響はこの依存表で判定する。過去の承認やレビューがどの版を対象にしたかを保持し、ハッシュだけを現在値へ書き換えて再利用しない。

## 中断と復旧

checkpointは工程資料と証跡をZIPに保存する。restoreは検証後に空の保存先へ復元する。既存ファイルへの上書き、ZIP外へのパス逸脱、シンボリックリンク、ハッシュ不一致を拒否する。

復元するのは工程記録であり、コードの巻き戻しではない。現在のブランチ・対象コード・Notion原本と照合し、不一致の工程は再検証する。会話から証跡を再生成しない。

## 変異テスト

詳細設計で重要な計算、境界条件、権限判断などについて、意図的な誤りと検出すべきテストを定義する。独立設計レビューで計画を確認する。対象がない場合も理由を独立レビューする。

mutateは非本番・使い捨てコピーで実行する。元のテストが成功してから一意な置換を適用する。成功したままの変異はテスト不足。タイムアウトや構文エラーなど実行不能を、期待した誤りを検出できた証拠としない。判定結果とログをtests.mdとgate.jsonへ紐付け、test-reviewで確認する。対象コマンドは外部へ副作用を持たないものに限定する。一時コピーはOSのサンドボックスではない。

## 保証範囲

機械検査は証跡の整合性を確認する。承認者の本人性、テストが要件を正しく表すこと、記録を編集できる利用者による改ざんへの耐性は別の問題であり、独立レビューとホスティング側の権限・CIで補う。

フックが無効でもCIから同じ検査を呼べる構成にする。フックの導入や信頼設定は自動変更しない。CIの必須チェック、保護ブランチ、本番の承認者設定は導入先の管理者が設定する。マージは一切実行しない。

Gitブランチ・base/head SHAの実体照合は[ブランチ準備規約](branching.md)に従い、開始・再開時にGeminiがgitで確認する。ランタイムのファイルハッシュ検査だけではGitの実ブランチ一致を保証しない。

releaseのcheckは本番操作の事前ゲート。合格だけでデプロイを自動実行せず、releaseスキルが承認された操作を行い、実施結果・動作確認をrelease.mdへ記録する。最終結果はcheckpointで保存する。

## 検査用ファイル一覧

以下は案件ルートからの相対パス。各段階で当該ファイルと参照先を直接読み、会話の要約で代用しない。

| パス | 作成・検査する工程 |
|---|---|
| `gate.json` | initで作成。全工程が読取。record/impact/advanceが進行を更新 |
| `evidence/approval.json` | 要件承認で作成。approve以降が照合 |
| `evidence/review-design.json` | 独立設計レビューで作成。review-design以降が照合 |
| `evidence/review-implementation.json` | 独立実装レビューで作成。review-implementation以降が照合 |
| `evidence/review-tests.json` | 独立テストレビューで作成。review-tests以降が照合 |
| `evidence/coverage.json` | テスト工程で作成。tests以降が照合 |
| `evidence/runs/<実行ID>.json` | runが作成。実行メタデータとログ/対象ハッシュ |
| `evidence/runs/<実行ID>.log` | runが作成。UT・結合・受入のIDを分ける |
| `evidence/mutations/<変異ID>.json` | mutateが作成。計画と変異の判定結果 |
| `evidence/mutations/<変異ID>.log` | mutateが作成。事前テストと変異テストのログ |
| `evidence/stages/<工程名>/<成果物パス>` | recordが保存。過去の承認・レビュー対象版 |
| `evidence/release-approval.json` | 本番承認で作成。releaseが環境・計画・対象と照合 |

カバレッジ原本・変換レポート、Notion取得資料、変異計画、変異対象外レビューは、導入先で確定した全パスをgate.jsonと該当工程MDへ記載する。`<実行ID>`などは実行前に確定する。
