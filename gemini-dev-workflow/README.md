# Gemini Development Workflow

Geminiで、要件定義から設計・実装・テスト・PR作成・リリース準備まで進めるワークフローです。既存のプロジェクトへインストールして使います。

**具体的な要件・設計・工数は、導入先のコードと環境を調べて決めます。**

[導入・更新の補足](docs/setup.md) · [工程・スキル・全ファイル一覧](docs/workflow-reference.md) · [Google公式出典](.gemini/workflow/references/sources.md)

## はじめる

必要なもの：**Python 3.10以上、Git、Gemini CLI（VS Codeは併用可）**。Windowsは`/tmp`が使えるWSL等で実行してください。

### 1. リポジトリを取得

`<repository-url>`を公開先URLに置き換え、開発対象とは別の場所へ取得します。

```sh
git clone <repository-url> gemini-dev-workflow
cd gemini-dev-workflow
```

### 2. クローンしたディレクトリで初期設定

**資料がNotionにある場合は、先に[Notionの接続手順・依頼プロンプト](.gemini/workflow/references/notion-setup.md)で接続してください。**

そのディレクトリでターミナルを開き、Geminiを起動します。

```sh
gemini
```

次の依頼を入力してください。

> GEMINI.mdを読み、ワークフローの初期設定をしてください。このディレクトリのファイル構造・コード・テンプレート・アーキテクチャ概念資料をすべて順次読み、可変領域を具体化してください。開発対象の資料がなければ場所を確認してください。初期設定が完成したら、開発には進まず結果を見せてください。

資料は現在のディレクトリ配下に配置するか、Geminiから読める対象プロジェクトの場所を指定します。読めない資料や未確定事項があれば、完成扱いにはしません。

### 3. 完成したワークフローで開発を開始

別のプロジェクトへ配置する場合だけ、初期設定後に導入します。

```sh
python .gemini/workflow/runtime/maintenance.py install --source . --target "/absolute/path/to/project"
python .gemini/workflow/runtime/maintenance.py install --source . --target "/absolute/path/to/project" --backup "/absolute/path/to/backups/install-001" --apply
```

別ディレクトリへ導入した場合は、そこでGeminiに初期設定の再確認を依頼します。

導入設定は通常の運用で対象のremote `develop`へ反映し、作業ツリーをクリーンにしてください。ワークフロー自身はマージしません。対象ディレクトリでGeminiを開き、依頼します。

```text
/gdw:start
```

初期設定は`/gdw:setup`、状況確認は`/gdw:status <案件パス>`、再開は`/gdw:resume <案件パス>`です。[操作コマンド一覧](docs/commands.md)で使い方を確認できます。

## 担当ごとのモデル

要件定義・設計・レビュー・検査は高性能モデル、それ以外は軽量モデルを使用します。各エージェントファイルの`model`欄が設定の正本です。

| クラス | 初期モデル |
|---|---|
| 高性能 | `gemini-3.1-pro-preview` |
| 軽量 | `gemini-3-flash-preview` |

[全担当の定義場所・切替・保守手順](.gemini/workflow/references/model-policy.md)を確認してください。指定モデルの利用可否と実際の選択を導入時に照合し、不一致なら停止します。

## プロジェクトごとに変わる部分

`.gemini/workflow/project/`が可変領域です。Geminiが調査して埋め、各工程が決められたファイルを読みます。

| ファイル | 記録する内容 |
|---|---|
| `profile.json` | 対象ディレクトリ・初期設定の完了状態 |
| `inventory.md` | 調査対象の全ファイル・読了状態・除外理由 |
| `structure.md` | ディレクトリ構造・コードの役割・依存関係 |
| `architecture.md` | アーキテクチャ・設計方針・開発規約 |
| `templates.md` | 各工程で使うテンプレートの場所と適用方法 |
| `commands.md` | ビルド・テスト・動作確認・リリースの設定 |
| `review.md` | 初期設定の確認結果・未解決事項 |

初期設定の工程記録は`/tmp/<repo-id>/workflow-setup/`に保存し、確定した設定を可変領域へ反映します。資料が変わった場合は再確認します。

## 開発の流れ

| 工程 | 行うこと |
|---|---|
| 要件定義 | `feature.xxx`を決め、最新developから分岐。環境調査後、一問一答で要件を整理 |
| 調査・見積もり | 対象コードを調べ、修正範囲と工数を算出。人が要件を承認 |
| 詳細設計 | 修正内容・テストケースを設計し、独立レビュー |
| 実装 | 設計に沿って修正し、要件と照合して独立レビュー |
| テスト・動作確認 | UT・結合テストを作成・実行。独立レビューと実環境での確認 |
| PR・リリース準備 | 工程資料と証跡をまとめ、PR添付用ZIPを作成 |
| 本番反映 | 対象コミット・環境・復旧手順について、人の承認後に実施 |

レビューで問題があれば、原因のある工程へ戻って修正します。

## 開発と運用を支える機能

| 機能 | できること |
|---|---|
| 環境診断 | CLI・担当モデル・設定・資料へのアクセスを確認 |
| 実機試験 | 小さな案件で質問・差戻し・実装・テスト・再開を試験 |
| 実行前フック | 未承認の実装・レビュー中の書込み・マージ操作を検査 |
| 安全な更新 | 個別設定を保持し、競合を提示。失敗時はバックアップから復元 |
| 資料の版管理 | Notion等の取得内容を固定し、変更・期限切れを検出 |
| 進捗表示 | 現在工程・停止理由・指摘・見積もりと実績をHTMLで表示 |
| 品質基準の監視 | テスト・カバレッジ設定・CIの変更を検出し、人の承認と照合 |

既存の工程ゲート・要件対応・独立レビュー・変異テスト・復旧と連動します。[操作手順と全ファイル一覧](.gemini/workflow/references/operations.md)

**実AIでの試験は認証済みの導入環境で実施してください。** 配布前の自動テストで使用した模擬ホストの結果を、実機合格とは扱いません。

## 運用のルール

- **マージは一切しません。** 要件確定と本番反映には人の承認が必要です。
- **レビューは別のエージェントまたはセッションで実施。** 必ず`requirements.md`と照合します。
- **UTは追加・変更処理の行・分岐100%。** 結合テストと要件のケース網羅性も確認します。
- **見積もりは1単位＝1時間。** C（AIなし人的工数）→B（Gemini経過時間）→A（Gemini人的工数）の順です。
- 同じ問題が修正・再レビュー3回で解消しなければ、停止して相談します。

## 記録と引き継ぎ

工程MDは`/tmp/<repo-id>/<branch>/`に保存します。修正時は同じファイルを更新し、履歴を追記します。次の工程は指定されたファイルを読み、会話の要約には依存しません。

最終成果物は、PR用の要約・報告書・工程資料・証跡ZIPです。**各スキルの読込・出力ファイルは、[省略なしの詳細一覧](docs/workflow-reference.md)で確認できます。**
